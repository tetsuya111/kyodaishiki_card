# 設計ドキュメントのベストプラクティス

`.kiro/specs/<feature-slug>/design.md` を書くときに従う原則。要件定義そのものの書き方は [docs/requirements-best-practices.md](requirements-best-practices.md) を参照。

## TL;DRを先頭に置く

設計ドキュメントの冒頭に2〜3文の要約を置く。レビュアー全員が全文を読むとは限らないため、概要だけで「何を・なぜ」変更するのかが伝わるようにする（Googleのデザインドック文化における一般的な慣習）。

## Non-Goalsを明記する

requirements.mdのNon-Goalsを引き継ぎつつ、この設計が「対応しない」技術的な範囲（例: 将来のスケール対応、他プラットフォーム対応など）を明記する。範囲を絞ることで設計の焦点が明確になる。

## 検討した代替案 (Alternatives Considered) を残す

採用した設計だけでなく、検討したが採用しなかった選択肢と、その理由を記録する。これはArchitecture Decision Record (ADR) の中心的な考え方であり、以下の効果がある。

- 後から「なぜこの設計にしたのか」を追跡できる（同じ議論を繰り返さない）
- レビュアーが「別の方法は検討したか」を確認しやすくなる
- 前提が変わった時に、過去に却下した案を再評価する材料になる

最低1つの代替案とその却下理由を書く。「特に代替案はない」場合も、検討した上でそう判断した旨を明記する。

## 横断的関心事 (Cross-Cutting Concerns) を独立したセクションにする

機能のコア設計（データモデル・API・UI）とは別に、以下の関心事を必ず独立したセクションとして検討する。実装が終わってから気づくと手戻りが大きいため、設計段階で明示的に扱う。

- **セキュリティ・プライバシー**: 認可境界、個人情報の扱い、新たな攻撃面
- **パフォーマンス・スケーラビリティ**: 想定負荷、ボトルネック、対策
- **オブザーバビリティ**: 障害・異常を検知するためのログ・メトリクス
- **テスト戦略**: 何をどう検証するか
- **ロールアウト計画**: 段階的リリース、マイグレーション、ロールバック手段

該当がない場合は空欄のままにせず、「影響なし」とその判断根拠を書く。

## 既存アーキテクチャとの整合性を確認する

新しい設計が既存の規約（[docs/architecture.md](architecture.md)）から外れる場合、意図的な逸脱なのか見落としなのかが分かるように、理由を明記する。

## 実装より前にレビューを受ける

design.mdの内容に合意してから実装（tasks.md）に進む。設計が固まっていない段階で実装を始めない（進め方の詳細は [.kiro/specs/README.md](../.kiro/specs/README.md)）。
