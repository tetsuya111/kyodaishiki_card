# 要件定義のベストプラクティス

`.kiro/specs/<feature-slug>/requirements.md` を書くときに従う原則。いつ・どういう順番で要件定義を進めるか（運用フロー）は [.kiro/specs/README.md](../.kiro/specs/README.md) を参照し、ここでは要件定義の中身（品質）の指針のみを扱う。

## 課題ドリブンで書く（Working Backwards）

「作りたいから作る」ではなく、誰のどんな課題を解決するのかという背景・課題から書き始める。Amazonの "Working Backwards"（顧客の課題から逆算して仕様を書く手法）と同様の考え方で、実装や機能そのものより先に「なぜ必要か」を明確にする。

## Non-Goals（やらないこと）を明記する

ゴールと対になる形で、意図的にスコープ外とすることを書く。Googleのデザインドック文化で広く使われる "Non-Goals" セクションと同じ考え方で、書かないことで生じる「なぜやらないのか」という後からの疑問を防ぎ、スコープクリープ（要件の際限ない拡大）を防止する。

## 成功指標を定義する

リリースして終わりにせず、「何をもって成功と判断するか」を定量指標で事前に決めておく。指標がなければ、機能追加後にその効果を検証する手段がなくなる。

## ユーザーストーリーの書き方

- 形式: `As a <ユーザー種別>, I want <したいこと>, so that <目的・理由>.`
- **INVEST原則**で書けているか確認する:
  - **Independent（独立）**: 他のストーリーに依存せず、単体で価値を持つ
  - **Negotiable（交渉可能）**: 実装方法を固定せず、詳細は設計フェーズに委ねる
  - **Valuable（価値がある）**: ユーザーや事業にとっての価値が明確
  - **Estimable（見積可能）**: 規模感を見積もれる程度に具体的
  - **Small（小さい）**: 1回のイテレーションで完了できる粒度
  - **Testable（検証可能）**: 満たされたかどうかを判定できる

## 受け入れ基準の書き方（EARS記法）

曖昧な自然言語ではなく、検証可能な条件文で書く。代表的なパターン:

| パターン | 書式 | 用途 |
| --- | --- | --- |
| 通常時 | `THE SYSTEM SHALL <振る舞い>` | 常に成り立つ振る舞い |
| イベント駆動 | `WHEN <イベント> THE SYSTEM SHALL <振る舞い>` | ユーザー操作やイベント発生時 |
| 状態駆動 | `WHILE <状態> THE SYSTEM SHALL <振る舞い>` | 特定の状態が続いている間 |
| 異常系 | `IF <条件> THEN THE SYSTEM SHALL <振る舞い>` | 例外・エラー・境界条件 |
| オプション機能 | `WHERE <条件が有効な場合> THE SYSTEM SHALL <振る舞い>` | 設定や権限で有効/無効が切り替わる機能 |

## 曖昧な表現を避ける

- 「使いやすい」「高速に」「適切に」のような主観的・検証不能な言葉を避け、具体的な数値や条件に置き換える（例: 「3秒以内に応答する」）。
- 1つの受け入れ基準には1つの検証可能な振る舞いだけを書く。複数条件を "and" で詰め込まない（テストが1つの合否で判定できなくなる）。

## 要件と設計を分離する

- requirements.mdには「何を実現するか (What)」だけを書き、「どう実装するか (How)」はdesign.mdに委ねる。実装方法を要件段階で決め打ちすると、設計の選択肢を不必要に狭めてしまう。

## スコープを明示する

- 含める範囲だけでなく、今回は対応しない範囲（スコープ外）も明記する。後工程での認識齟齬や、意図しない機能追加（スコープクリープ）を防ぐ。

## 機能要件と非機能要件を分ける

- 機能要件（何ができるか）と非機能要件（性能・セキュリティ・可用性などの制約）を混在させない。非機能要件がある場合はセクションを分けて明記する。

## トレーサビリティを保つ

- 各受け入れ基準が、design.mdのどの設計要素・tasks.mdのどのタスクに対応するかを追跡できるようにする。要件に対応しない実装や、実装されない要件がないか確認する。

## レビューのタイミング

- requirements.mdの内容に合意してから設計（design.md）に進む。要件が固まっていない段階で設計・実装を始めない（進め方の詳細は [.kiro/specs/README.md](../.kiro/specs/README.md)）。
